## 1.2. คำถามท้ายการทดลอง (Post-Lab Questions)

1. เหตุใด IP Address เริ่มต้นของ ESP32 SoftAP จึงเป็น `192.168.4.1` และ DHCP Server บน ESP32 เริ่มแจกจ่าย IP ที่หมายเลขใด?
ตอบ: ระบบสามารถตรวจสอบ RSSI ของอุปกรณ์ก่อนอนุญาตให้เช็กชื่อ โดยกำหนดให้ต้องมีระดับสัญญาณถึงเกณฑ์ที่กำหนด จึงช่วยจำกัดการเช็กชื่อจากอุปกรณ์ที่อยู่ไกล อย่างไรก็ตาม RSSI เพียงอย่างเดียวไม่สามารถป้องกันการฝากเช็กชื่อได้ทั้งหมด

2. สมาชิกตัวแปร `mac` ในโครงสร้าง `wifi_event_ap_staconnected_t` สามารถนำไปประยุกต์ใช้ทำระบบความปลอดภัยขั้นสูง (เช่น MAC Filtering) ได้อย่างไร?
ตอบ: ค่า -55 dBm เป็นเกณฑ์ที่ใช้คัดกรองสัญญาณที่ค่อนข้างแรง ซึ่งอาจบ่งชี้ว่าอุปกรณ์อยู่ใกล้ ESP32 อย่างไรก็ตาม ระยะทางจริงขึ้นอยู่กับสิ่งกีดขวาง ตำแหน่งอุปกรณ์ และสภาพแวดล้อม จึงต้องทดสอบเพื่อหาเกณฑ์ที่เหมาะสม
  
3. หากมี Client พยายามเชื่อมต่อเป็นเครื่องที่ 5 (เกินค่า `max_connection = 4`) จะเกิดเหตุการณ์ใดขึ้นในระดับสัญญาณวิทยุ?
ตอบ: สามารถพัฒนาระบบให้บันทึกข้อมูลการเข้าเรียนลงฐานข้อมูล เพิ่มระบบยืนยันตัวตนด้วยบัญชีนักศึกษา ใช้ RSSI ร่วมกับ QR Code และ Timestamp รวมถึงสร้าง Dashboard สำหรับแสดงประวัติการเข้าเรียนแบบเรียลไทม์ เพื่อเพิ่มความสะดวกและลดโอกาสการทุจริตในการเช็กชื่อ

## 2.2.คำถามท้ายการทดลอง (Post-Lab Questions)

1. เมื่อลดระดับ Tx Power ลงจาก 20 dBm เหลือ 2 dBm ค่า RSSI ลดลงกี่ dBm และส่งผลต่อความเร็ว Throughput อย่างไร?
ตอบ: จากข้อมูลตัวอย่าง RSSI ลดลงจาก -35 dBm เป็น -65 dBm หรือลดลง 30 dB ส่วน Throughput ลดลงจาก 850 Kbps เป็น 250 Kbps เนื่องจากระดับสัญญาณที่ลดลงอาจส่งผลให้ประสิทธิภาพการรับส่งข้อมูลลดลง

2. เหตุใดในระดับ RSSI ที่อ่อนกว่า `-80 dBm` ความเร็ว Throughput ถึงตกลงอย่างกะทันหันในโปรโตคอล TCP?
ตอบ: เนื่องจากแพ็กเก็ตสูญหายและต้องส่งข้อมูลซ้ำมากขึ้น ทำให้ TCP ลดอัตราการส่งข้อมูล ส่งผลให้ Throughput ลดลง

3. สมการ Regression ที่ได้จากการทดลองสามารถนำไปประยุกต์ใช้ทำนายคุณภาพการเชื่อมต่อในแอปพลิเคชัน IoT ได้อย่างไร?
ตอบ: สามารถนำข้อมูล RSSI และ Throughput มาสร้างสมการ Regression เพื่อประมาณความเร็วในการรับส่งข้อมูลจากระดับสัญญาณ และนำไปใช้ปรับการทำงานของอุปกรณ์ IoT ให้เหมาะสมกับคุณภาพเครือข่าย

## 3. 2.คำถามท้ายการทดลอง (Post-Lab Questions)

1. เหตุใดการใช้ **FreeRTOS Queue** จึงมีความปลอดภัย (Thread-Safe) มากกว่าการใช้ตัวแปรแบบ Global ในการรับส่งข้อมูลระหว่างสอง Task?
ตอบ: FreeRTOS Queue มีกลไกจัดการการรับส่งข้อมูลระหว่าง Task อย่างปลอดภัย ช่วยป้องกันการเข้าถึงข้อมูลพร้อมกันและลดปัญหาข้อมูลผิดพลาดที่อาจเกิดจากการใช้ตัวแปร Global ร่วมกันโดยไม่มีการป้องกัน

2. ค่า **Stack High Water Mark** มีประโยชน์อย่างไรในการตรวจวินิจฉัยปัญหาบั๊กในระบบเรียลไทม์ (RTOS)?
ตอบ: ใช้ตรวจสอบปริมาณ Stack ที่เหลืออยู่ของแต่ละ Task ช่วยประเมินการใช้หน่วยความจำและตรวจหาความเสี่ยง Stack Overflow ซึ่งอาจทำให้ระบบทำงานผิดพลาดหรือหยุดทำงานได้

3. หาก `vSensorTask` ส่งข้อมูลเร็วมาก (เช่น ทุก 10ms) แต่ `vNetworkTask` ส่งข้อมูลออก Wi-Fi ได้ช้า (เช่น ใช้เวลา 500ms) จะเกิดอะไรขึ้นกับ Queue และระบบจะรับมืออย่างไร?
ตอบ: ข้อมูลจะเข้าสู่ Queue เร็วกว่าที่ Network Task จะประมวลผล ทำให้ Queue เต็มและข้อมูลใหม่อาจถูกปฏิเสธหรือสูญหาย ระบบจึงควรกำหนดขนาด Queue ให้เหมาะสม ตรวจสอบค่าที่ส่งกลับจากการส่งข้อมูล และเลือกนโยบายจัดการข้อมูลเมื่อ Queue เต็มให้เหมาะกับงาน

## 4.3. คำถามท้ายการทดลอง (Post-Lab Questions)

1. เหตุใดจึงต้องใช้ **Mutex** ในการป้องกันการเข้าถึงตัวแปร `g_latest_data` ร่วมกันระหว่าง `vNetworkTask` และ HTTP Handler? ถ้าไม่ใช้จะเกิดอะไรขึ้น?
ตอบ: เพราะ vNetworkTask และ HTTP Handler อาจอ่านหรือเขียนข้อมูลพร้อมกัน หากไม่มี Mutex อาจเกิด Race Condition ทำให้ข้อมูลไม่สอดคล้องกันหรืออ่านค่าได้ไม่ครบถ้วน

2. `esp_http_server` รัน Handler บน Thread ใด — เป็น Thread เดียวกับ FreeRTOS Task ของเราหรือไม่?
ตอบ: HTTP Handler ทำงานในบริบทของ Server Task ที่ esp_http_server สร้างและจัดการให้ ซึ่งเป็น FreeRTOS Task เช่นกัน แต่โดยทั่วไปเป็นคนละ Task กับ Task ที่ผู้พัฒนาสร้างขึ้นเอง

3. การที่ Dashboard ใช้ `<meta http-equiv="refresh" content="2">` แทนที่จะใช้ JavaScript `fetch()` มีข้อดีและข้อเสียอย่างไร?
ตอบ: ข้อดีคือเขียนโปรแกรมง่ายและไม่ต้องใช้ JavaScript ในการดึงข้อมูล ส่วนข้อเสียคือหน้าเว็บต้องโหลดใหม่ทุก 2 วินาที ทำให้เกิดการใช้แบนด์วิดท์มากขึ้นและการแสดงผลอาจไม่ต่อเนื่องเท่าการใช้ fetch()

## 5.2. คำถามท้ายการทดลอง (Post-Lab Questions)


1. การใช้ **RF Signal Proximity (RSSI)** ร่วมกับ **HTTP Web Server** บน ESP32 แก้ปัญหาการฝากเช็กชื่อแทนกันในห้องเรียนได้อย่างไร?
ตอบ: ระบบสามารถตรวจสอบ RSSI ของอุปกรณ์ก่อนอนุญาตให้เช็กชื่อ โดยกำหนดให้ต้องมีระดับสัญญาณถึงเกณฑ์ที่กำหนด จึงช่วยจำกัดการเช็กชื่อจากอุปกรณ์ที่อยู่ไกล อย่างไรก็ตาม RSSI เพียงอย่างเดียวไม่สามารถป้องกันการฝากเช็กชื่อได้ทั้งหมด

2. เหตุใดระดับเกณฑ์ RSSI ที่ `-55 dBm` จึงเหมาะสมสำหรับการระบุตำแหน่งอุปกรณ์ให้อยู่ภายในรัศมีโต๊ะปฏิบัติการ?
ตอบ: ค่า -55 dBm เป็นเกณฑ์ที่ใช้คัดกรองสัญญาณที่ค่อนข้างแรง ซึ่งอาจบ่งชี้ว่าอุปกรณ์อยู่ใกล้ ESP32 อย่างไรก็ตาม ระยะทางจริงขึ้นอยู่กับสิ่งกีดขวาง ตำแหน่งอุปกรณ์ และสภาพแวดล้อม จึงต้องทดสอบเพื่อหาเกณฑ์ที่เหมาะสม

3. หากต้องการต่อยอดมินิโปรเจกต์นี้ในอนาคต ให้สามารถบันทึกข้อมูลการเข้าเรียนลงระบบ Cloud (เช่น Google Sheets หรือ Firebase) จะต้องเพิ่มส่วนเชื่อมต่อใดบ้าง?
ตอบ: สามารถพัฒนาระบบให้บันทึกข้อมูลการเข้าเรียนลงฐานข้อมูล เพิ่มระบบยืนยันตัวตนด้วยบัญชีนักศึกษา ใช้ RSSI ร่วมกับ QR Code และ Timestamp รวมถึงสร้าง Dashboard สำหรับแสดงประวัติการเข้าเรียนแบบเรียลไทม์ เพื่อเพิ่มความสะดวกและลดโอกาสการทุจริตในการเช็กชื่อ
