## 8. คำถามท้ายการทดลอง (Post-Lab Questions)

1. เหตุใดจึงต้องใช้ **Mutex** ในการป้องกันการเข้าถึงตัวแปร `g_latest_data` ร่วมกันระหว่าง `vNetworkTask` และ HTTP Handler? ถ้าไม่ใช้จะเกิดอะไรขึ้น?
```
ต้องใช้ Mutex เพราะ g_latest_data เป็นตัวแปร Global ที่ถูกเข้าถึงพร้อมกันจากสอง Context ที่ต่างกัน คือ vNetworkTask เขียนค่าใหม่ และ HTTP Handler อ่านค่าไปแสดงผล ซึ่งอาจทำงานคาบเกี่ยวกันได้ทุกเมื่อ หากไม่ใช้ Mutex อาจเกิด Race Condition โดยเฉพาะถ้าตัวแปรเป็น struct หรือ string ที่มีหลาย field เพราะขณะที่ Task หนึ่งกำลังเขียนค่าอยู่ ยังเขียนไม่ครบทุก field แต่ถูก Context Switch ไปให้อีก Task อ่านค่ากลางคัน จะทำให้ได้ข้อมูลที่ค่าบาง field เป็นค่าเก่า บาง field เป็นค่าใหม่ผสมกัน (Data Corruption) ส่งผลให้ Dashboard แสดงผลข้อมูลที่ไม่ถูกต้องหรือไม่สอดคล้องกัน
```
2. `esp_http_server` รัน Handler บน Thread ใด — เป็น Thread เดียวกับ FreeRTOS Task ของเราหรือไม่?
```
esp_http_server จะสร้าง FreeRTOS Task แยกต่างหากขึ้นมาเองสำหรับรัน HTTP Server มักตั้งชื่อ Task ว่า httpd ดังนั้น Handler ที่เราเขียนจะถูกเรียกทำงานบน Task ของ HTTP Server เอง ไม่ใช่ Task เดียวกับ vNetworkTask หรือ vSensorTask ที่เราสร้างขึ้น นี่คือเหตุผลสำคัญที่ทำให้การเข้าถึงตัวแปรร่วมอย่าง g_latest_data ต้องมีการป้องกันด้วย Mutex เพราะเป็นการเข้าถึงข้ามระหว่าง Task จริงๆ ไม่ใช่แค่ Function เรียกใน Task เดียวกัน
```
3. การที่ Dashboard ใช้ `<meta http-equiv="refresh" content="2">` แทนที่จะใช้ JavaScript `fetch()` มีข้อดีและข้อเสียอย่างไร?
```
ข้อดีของ meta refresh คือใช้งานง่าย เขียนโค้ดน้อย ไม่ต้องพึ่ง JavaScript จึงเหมาะกับอุปกรณ์ฝังตัวที่ต้องการความเรียบง่ายและประหยัดทรัพยากร แต่ข้อเสียคือทำให้หน้าเว็บโหลดใหม่ทั้งหน้า Full Page Reload ทุกครั้ง ทำให้เกิดการกระพริบ Flickering เสียการโฟกัส Input หรือตำแหน่ง Scroll ที่ผู้ใช้ทำไว้ และสิ้นเปลืองการรับส่งข้อมูล/แบนด์วิดท์มากกว่า เพราะต้องโหลด HTML, CSS ทั้งหมดใหม่ทุกรอบ ในขณะที่ fetch() สามารถดึงเฉพาะข้อมูลที่เปลี่ยนแปลง เช่น JSON มาอัปเดตเฉพาะส่วนของหน้าเว็บได้ ทำให้ประสบการณ์ผู้ใช้ลื่นไหลกว่าและประหยัดทรัพยากรเครือข่ายมากกว่า
```
