### คำถามท้ายการทดลอง (Post-Lab Questions)

#### 1. เหตุใดการใช้ FreeRTOS Queue จึงมีความปลอดภัย (Thread-Safe) มากกว่าการใช้ตัวแปรแบบ Global ในการรับส่งข้อมูลระหว่างสอง Task?
**ตอบ:** มีกลไกป้องกันการแย่งใช้ข้อมูล (Mutual Exclusion & Thread-Safe): ภายใน Queue มี Critical Section จัดการล็อกข้อมูลโดยอัตโนมัติ ทำให้หมดปัญหา Race Condition หรือข้อมูลเสียหายเมื่อถูกขัดจังหวะ (Context Switch) ขณะอ่าน/เขียน

คัดลอกข้อมูลแบบ Pass-by-Copy: คัดลอกค่าข้อมูลลงบัฟเฟอร์ของคิวทันที ทำให้ Task ผู้ส่งสามารถอัปเดตหรือใช้ตัวแปรเดิมต่อได้โดยไม่กระทบข้อมูลที่รออ่าน

รองรับการบล็อก Task อัตโนมัติ (Task Blocking): สั่งให้ Task รอรับข้อมูลได้แบบ Zero-CPU (Blocked state) โดยไม่ต้องเขียนลูปเช็กแบบ Polling ซึ่งสิ้นเปลืองทรัพยากร

#### 2. ค่า Stack High Water Mark มีประโยชน์อย่างไรในการตรวจวินิจฉัยปัญหาบั๊กในระบบเรียลไทม์ (RTOS)?
**ตอบ:** ป้องกัน Stack Overflow: บอกปริมาณ Stack ขั้นต่ำสุดที่เคยเหลือรอด (หน่วยเป็น Words) ทำให้รู้ว่า Task นั้นใกล้เกิดปัญหาหน่วยความจำล้นจนทำให้ระบบแครชหรือไม่

ช่วย Optimize หน่วยความจำ RAM: ช่วยประเมินว่ากำหนดขนาด Stack ให้ Task มากเกินความจำเป็นหรือไม่ เพื่อปรับลดขนาดลงและคืนพื้นที่ RAM ให้กับระบบได้อย่างเหมาะสมและปลอดภัย

#### 3. หาก `vSensorTask` ส่งข้อมูลเร็วมาก (เช่น ทุก 10ms) แต่ `vNetworkTask` ส่งข้อมูลออก Wi-Fi ได้ช้า (เช่น ใช้เวลา 500ms) จะเกิดอะไรขึ้นกับ Queue และระบบจะรับมืออย่างไร?
**ตอบ:** สิ่งที่จะเกิดขึ้นกับ Queue: คิวจะเต็มอย่างรวดเร็ว (Queue Full) เพราะอัตราการผลิตข้อมูลสูงกว่าอัตราการดึงข้อมูลไปประมวลผล

การรับมือของระบบ (ขึ้นอยู่กับการตั้งค่าเวลา xTicksToWait ในฟังก์ชัน xQueueSend):

กรณีตั้งเวลารอ (xTicksToWait > 0): vSensorTask จะถูกสั่งบล็อก (Blocked State) เพื่อรอจนกว่าจะมีที่ว่างในคิว แต่หากพ้นเวลา Timeout ที่กำหนด ข้อมูลชุดใหม่จะถูกทิ้ง (Drop Packet)

กรณีไม่รอ (xTicksToWait = 0): ฟังก์ชันจะส่งคืนค่า errQUEUE_FULL ทันที ข้อมูลชุดใหม่จะสูญหาย (Data Loss)

แนวทางแก้ไขเชิงสถาปัตยกรรม: เพิ่มขนาดบัฟเฟอร์คิว, ใช้ฟังก์ชัน xQueueOverwrite() เพื่อเก็บเฉพาะค่าล่าสุด, หรือปรับลดอัตราการสุ่มอ่านเซนเซอร์ให้เหมาะสมกับความเร็วเครือข่าย
