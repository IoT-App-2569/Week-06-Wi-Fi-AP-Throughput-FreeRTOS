### คำถามท้ายการทดลอง (Post-Lab Questions)

#### 1. เหตุใดจึงต้องใช้ Mutex ในการป้องกันการเข้าถึงตัวแปร `g_latest_data` ร่วมกันระหว่าง `vNetworkTask` และ HTTP Handler? ถ้าไม่ใช้จะเกิดอะไรขึ้น?
**ตอบ:** เหตุผลที่ต้องใช้: เพื่อรับประกันความปลอดภัยของข้อมูล (Thread-Safe) ให้การอ่านและเขียนตัวแปรโครงสร้างข้อมูลขนาดหลายฟิลด์เกิดขึ้นแบบ Atomic (ทำเสร็จสิ้นสมบูรณ์ทีละฝั่ง ไม่ถูกขัดจังหวะ)

ถ้าไม่ใช้จะเกิดอะไรขึ้น: เกิด Race Condition โดยหาก HTTP Handler กำลังอ่านข้อมูลเพื่อส่งออกเป็น JSON จังหวะเดียวกับที่ vNetworkTask โดน Context Switch เข้ามาเขียนทับ ข้อมูลที่ส่งออกไปจะฉีกขาดหรือไม่สอดคล้องกัน (Data Inconsistency / Torn Read) เช่น ได้อุณหภูมิของรอบใหม่ แต่ได้ค่าความชื้นและ timestamp ของรอบเก่า

#### 2. `esp_http_server` รัน Handler บน Thread ใด — เป็น Thread เดียวกับ FreeRTOS Task ของเราหรือไม่?
**ตอบ:** รันบน Thread ใด: รันบน Thread/Task เฉพาะของตัวเว็บเซิร์ฟเวอร์เอง (มีชื่อ Task ภายในว่า httpd) ซึ่งถูกสร้างขึ้นอัตโนมัติเมื่อเรียกใช้ฟังก์ชัน httpd_start()

เป็น Thread เดียวกับ Task ของเราหรือไม่: ไม่ใช่ เป็นคนละ Task กันโดยสิ้นเชิงกับ Task ที่เราสร้างขึ้นเอง (เช่น vNetworkTask หรือ SensorCollectorTask) จึงทำงานแบบแยกอิสระ (Concurrent) และจำเป็นต้องใช้กลไกการซิงโครไนซ์ข้อมูลอย่าง Mutex ในการเข้าถึงข้อมูลร่วมกัน

#### 3. การที่ Dashboard ใช้ `<meta http-equiv="refresh" content="2">` แทนที่จะใช้ JavaScript `fetch()` มีข้อดีและข้อเสียอย่างไร?
**ตอบ:** ข้อดีของ <meta http-equiv="refresh">:

เขียนโค้ดง่าย: ไม่ต้องพึ่งพา JavaScript หรือเขียนสคริปต์จัดการ DOM ในฝั่ง Client

ความเข้ากันได้สูง: เบราว์เซอร์ทุกประเภท (รวมถึงเบราว์เซอร์รุ่นเก่าหรืออุปกรณ์ที่ปิดการทำงานของ JS) สามารถโหลดหน้าใหม่ได้ทันที

ข้อเสียของ <meta http-equiv="refresh">:

สิ้นเปลืองแบนด์วิดท์และทรัพยากร ESP32: ต้องส่งโค้ด HTML, CSS และโครงสร้างหน้าเว็บทั้งหมดซ้ำใหม่ทุก 2 วินาที แทนที่จะส่งเฉพาะก้อนข้อมูล JSON ขนาดเล็ก

ประสบการณ์ผู้ใช้ไม่ราบรื่น (UI Flashing): หน้าจอจะกะพริบหรือโหลดหน้าซ้ำทั้งหน้าทุกครั้งที่รีเฟรช ไม่นิ่งเหมือนการใช้ JavaScript fetch() ที่ดึงเฉพาะข้อมูลมาอัปเดตเฉพาะจุดแบบเบื้องหลัง (Asynchronous)
