### คำถามท้ายการทดลอง (Post-Lab Questions)

#### 1. การใช้ RF Signal Proximity (RSSI) ร่วมกับ HTTP Web Server บน ESP32 แก้ปัญหาการฝากเช็กชื่อแทนกันในห้องเรียนได้อย่างไร?
**ตอบ:** ตรวจสอบตำแหน่งทางกายภาพจริง (Physical Presence Verification): บังคับให้อุปกรณ์ต้องอยู่ใกล้ ESP32 ภายในระยะของสัญญาณวิทยุ (RSSI $\ge$ -55 dBm) ณ ขณะที่กดยืนยันตัวตน ทำให้ไม่สามารถแชร์ลิงก์หรือฝากเพื่อนที่อยู่นอกห้อง/นอกอาคารกดเช็กชื่อแทนผ่านเครือข่ายอินเทอร์เน็ตได้ผูกตัวตนเข้ากับฮาร์ดแวร์จริง: ตรวจสอบค่า MAC Address คู่กับความแรงสัญญาณวิทยุ (RSSI) ในระดับ Link Layer โดยตรง ซึ่งค่าดังกล่าววัดได้จากตัวรับส่งสัญญาณของบอร์ด ESP32 เอง ไม่ใช่ค่าพิกัด GPS หรือข้อมูลที่ผู้ใช้สามารถปลอมแปลง (Spoof) ผ่านหน้าเว็บเบราว์เซอร์ได้ง่าย

#### 2. เหตุใดระดับเกณฑ์ RSSI ที่ `-55 dBm` จึงเหมาะสมสำหรับการระบุตำแหน่งอุปกรณ์ให้อยู่ภายในรัศมีโต๊ะปฏิบัติการ?
**ตอบ:** สอดคล้องกับคุณสมบัติการลดทอนของสัญญาณ (Path Loss): ในย่านความถี่ 2.4 GHz สัญญาณวิทยุจะลดทอนอย่างรวดเร็วในระยะใกล้ (Near-Field Path Loss) โดยระดับความแรง 
≥−55 dBm จะเกิดขึ้นเมื่ออุปกรณ์อยู่ห่างจากตัวส่งไม่เกินรัศมีประมาณ 1–2 เมตรเท่านั้น (ระดับโต๊ะปฏิบัติการ)

ป้องกันสัญญาณทะลุผนังหรือข้ามห้อง (Margin of Isolation): สัญญาณที่ส่งมาจากนอกห้องเรียนหรือทางเดินหน้าห้อง แม้จะเร่งกำลังส่งสูงสุด (Tx Power 20 dBm) ก็มักจะถูกลดทอนผ่านผนังและระยะทางจนตกลงไปต่ำกว่า 
−65 dBm เกณฑ์ 
−55 dBm จึงเป็นจุดตัดที่มี Margin สูงพอที่จะคัดกรองอุปกรณ์นอกพื้นที่ออกได้อย่างแม่นยำ

รองรับความแปรปรวนจากสภาพแวดล้อม (Multipath Fading & Shadowing): หากตั้งค่าสูงเกินไป (เช่น 
≥−40 dBm) อุปกรณ์ที่วางอยู่บนโต๊ะจริงอาจเชื่อมต่อไม่ติดหากมีมือหรือร่างกายของผู้ใช้บังแนวสายตา (Line of Sight) ค่า 
−55 dBm จึงเป็นจุดสมดุลที่ดีที่สุดระหว่างความเข้มงวดของระยะทางและความเสถียรในการใช้งานจริง

#### 3. หากต้องการต่อยอดมินิโปรเจกต์นี้ในอนาคต ให้สามารถบันทึกข้อมูลการเข้าเรียนลงระบบ Cloud (เช่น Google Sheets หรือ Firebase) จะต้องเพิ่มส่วนเชื่อมต่อใดบ้าง?
**ตอบ:** 1. การเชื่อมต่อโครงสร้างเครือข่าย (Network Dual-Mode / Uplink):

สลับโหมด Wi-Fi ของ ESP32 ให้ทำงานแบบ Wi-Fi AP + STA Mode (Coexistence) เพื่อให้บอร์ดทำหน้าที่ปล่อย SoftAP ให้สมาร์ตโฟนเชื่อมต่อเช็กชื่อ พร้อมกับเชื่อมต่อ Station (STA) ออกสู่อินเทอร์เน็ตผ่าน Wi-Fi ของอาคารหรือเราเตอร์ห้องเรียนไปพร้อมกัน

2. โปรโตคอลและไลบรารีสื่อสารระดับ Application Layer (Data Transport):

HTTPS Client (esp_http_client): เพิ่มโค้ดส่งคำขอแบบ HTTP POST พร้อมแนบ Payload เป็น JSON ข้อมูลการเช็กชื่อ (MAC, Timestamp, RSSI, Status) ส่งไปยัง REST API, Firebase Realtime Database / Firestore REST API หรือ Google Apps Script Web App (สำหรับบันทึกเข้า Google Sheets)

MQTT Client (esp-mqtt): ทางเลือกเสริมกรณีต้องการส่งข้อมูลแบบ Event-Driven เข้า IoT Cloud Broker (เช่น HiveMQ, AWS IoT) ก่อนส่งต่อไปยังฐานข้อมูลปลายทาง

3. ระบบความปลอดภัยและการเข้ารหัส (Transport Layer Security - TLS/SSL):

เปิดใช้งาน mbedTLS บน ESP-IDF พร้อมนำเข้าใบรับรองความปลอดภัย Root CA Certificate (เช่น ISRG Root X1 ของ Let's Encrypt หรือ Google Trust Services) เพื่อให้ ESP32 สามารถทำ Handshake ตรวจสอบสิทธิ์และรับส่งข้อมูลผ่าน HTTPS (Port 443) กับเซิร์ฟเวอร์ Cloud ได้อย่างปลอดภัย

4. ระบบเวลาจริงและการจัดการคิวส่งข้อมูล (Time Synchronization & Queue Buffer):

SNTP Client (esp_sntp): ซิงโครไนซ์เวลาสากลจาก NTP Server ผ่านอินเทอร์เน็ต เพื่อให้ได้ Timestamp จริง (วัน/เดือน/ปี และเวลาตาม Timezone ประเทศไทย) แทนที่การใช้ค่ามิลลิวินาทีจากระบบบูต

FreeRTOS Queue Buffer: สร้างคิวพักข้อมูลการเช็กชื่อใน RAM หรือบันทึกลง Flash (NVS / SPIFFS) ชั่วคราว เพื่อรองรับกรณีอินเทอร์เน็ตของอาคารขัดข้อง ช่วยป้องกันข้อมูลการเข้าเรียนสูญหายก่อนที่ระบบจะส่งข้อมูลขึ้น Cloud สำเร็จ
