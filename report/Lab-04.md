## 8. คำถามท้ายการทดลอง (Post-Lab Questions)

1. เหตุใดจึงต้องใช้ **Mutex** ในการป้องกันการเข้าถึงตัวแปร `g_latest_data` ร่วมกันระหว่าง `vNetworkTask` และ HTTP Handler? ถ้าไม่ใช้จะเกิดอะไรขึ้น?
```
Mutex  ถูกนำมาใช้เพื่อป้องกันปัญหา Race Condition เนื่องจากการทำงานของ Task ทั้งสองเกิดขึ้นพร้อมกันอย่างอิสระ หากไม่ใช้ Mutex อาจเกิดเหตุการณ์ที่ vNetworkTask กำลังเขียนอัปเดตข้อมูลลงไปได้เพียงครึ่งเดียว แล้ว HTTP Handler เข้ามาดึงข้อมูลไปแสดงผลพอดี ทำให้ผู้ใช้บนหน้าเว็บได้รับข้อมูลที่ผิดเพี้ยนหรือไม่สอดคล้องกัน
```

2. `esp_http_server` รัน Handler บน Thread ใด — เป็น Thread เดียวกับ FreeRTOS Task ของเราหรือไม่?
```
esp_http_server ไม่ได้รันบน Thread เดียวกับ Task ที่เราสร้างขึ้น เมื่อมีการเรียกคำสั่ง httpd_start() ตัวระบบจะทำการสร้าง FreeRTOS Task หรือ Thread ใหม่แยกต่างหาก เพื่อคอยจัดการกับ Request ที่เข้ามาโดยเฉพาะ ดังนั้น HTTP Handler จึงทำงานอยู่บน Thread ของเซิร์ฟเวอร์เอง แยกขาดจาก vSensorTask และ vNetworkTask อย่างสิ้นเชิง
```

3. การที่ Dashboard ใช้ `<meta http-equiv="refresh" content="2">` แทนที่จะใช้ JavaScript `fetch()` มีข้อดีและข้อเสียอย่างไร?
```
ข้อดี :
เขียนโค้ดได้ง่ายและสั้นมาก ไม่จำเป็นต้องมีความรู้เรื่อง JavaScript หรือกระบวนการ Asynchronous ก็สามารถทำให้หน้าเว็บอัปเดตตัวเองได้ และรองรับการทำงานบนเบราว์เซอร์รุ่นเก่าได้ดี

ข้อเสีย :
การใช้ meta refresh จะบังคับให้เบราว์เซอร์โหลดหน้าเว็บใหม่ทั้งหมด ทุก ๆ 2 วินาที ทำให้หน้าจอเกิดอาการกระพริบ  สิ้นเปลืองแบนด์วิดท์ของเครือข่าย Wi-Fi และเพิ่มภาระการประมวลผลให้กับบอร์ด ESP32 โดยไม่จำเป็น เมื่อเทียบกับการใช้ JavaScript fetch() ที่จะดึงแค่แพ็กเก็ตข้อมูล JSON ขนาดเล็กมาอัปเดตเฉพาะตัวเลขบนหน้าจอเท่านั้น
```
